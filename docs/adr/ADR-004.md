# ADR-004: Use a kinematic character controller; reserve BepuPhysics for server-side traps
**Date:** 2026-10-08 **Status:** proposed
### Context
Planned traps (a rolling boulder, crates) need real rigid-body physics. But the character is predicted on the client (ADR-001, ADR-002), and no physics engine produces identical results in JavaScript and C#. Putting the character in a physics engine would make prediction rubber-band permanently. Phase 2 also replaces the debug boxes with Blender GLB models, which raises the question of whether physics should use those meshes.

### Decision
The character uses a hand-written kinematic controller: a circle against axis-aligned boxes, sliding along X and then Z. It lives in the shared mirror and is never a physics body. Dynamic trap objects run in BepuPhysics v2 on the server only. Their position and rotation travel in snapshots, and clients interpolate them without predicting them. Physics never uses GLB meshes: every collision shape is a simple primitive that comes from the Blender collider pipeline (ADR-005), and the server never loads a GLB.

### Consequences
Character movement stays deterministic, Bepu never reaches the client, and swapping art can't change gameplay. Physics objects don't push characters for free, so "the boulder hits the player" has to be a server-side rule. The server's two collision worlds (kinematic walls and Bepu static walls) must both be built from the same generated collider data, and each GLB's origin must match its body's center or the visual drifts from the physics. I'd revisit this decision if gameplay needed characters to be physically shoved.
