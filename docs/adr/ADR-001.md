# ADR-001: Use Server as Authority for Game Loop with Client Prediction
**Date:** 2026-09-02 **Status:** accepted
### Context
Heist is a multiplayer browser game for 2-4 players who cooperate to achieve goals, built by one developer in one semester. Every player must get the same outcome when the team wins or a trap catches someone. Browser clients can't be relied on for low latency. Someone has to own the game state, and that decision shapes the hosting, the code layout, and where the game rules live.

### Decision
The ASP.NET server owns the game state and simulates each room on a fixed 20Hz tick. Clients send only numbered input intentions over SignalR. The local player's movement is predicted and then reconciled against server snapshots, and remote players are drawn by interpolating between snapshots.

### Consequences
Win and trap rules live in one place, C#, and cheating by sending positions is impossible. In exchange, the game needs an always-on host that supports WebSockets, and movement code must exist in both JS and C# (see ADR-002). Client-Authority is too easy to cheat, peer-to-peer's is unstable with NAT and host migration, and lockstep stalls with slowest latency thus they are rejected. I'd revisit this decision if a competitive mode made the 100ms delay on remote players unacceptable.
